# V51 规格书逐条落地实现（方案 A）设计文档

日期：2026-05-03  
目标：按 [V51_Specification.md](file:///workspace/doc/V51_Specification.md) 从头到尾逐条落地实现，并将结果作为主干（main）版本基线。

## 1. 范围与原则

### 1.1 以规格书为唯一真源
- 以 [V51_Specification.md](file:///workspace/doc/V51_Specification.md) 为准。
- 任何功能“存在但与规格冲突”都视为缺陷：需要改为符合规格书，而不是在规格之外扩展。

### 1.2 最高铁律（必须满足）
- 自定义方块数量严格为 2：`power_core`、`trade_terminal`。
- 所有交互功能必须收敛到这两个方块的 GUI 标签页（Tab）。
- Minecraft/Forge 版本约束：1.20.1 Forge 47.4.16；禁止使用 1.21+ 写法。

### 1.3 Server Authoritative（安全与一致性）
- 服务器是唯一权威数据源。
- 客户端只能“展示 + 发起请求”，不能直接修改任何玩家数据、经济数据、契约关系、签证/越界状态。
- 任何 C2S 数据包与命令必须在服务端做强校验（权限/距离/身份/输入范围/节流）。

### 1.4 数据中心化
- 玩家状态仅存储于 `PlayerDataCapability`。
- 世界级数据存储在 `WorldData(SavedData)` 等 SavedData 内。
- 禁止在 GUI/BlockEntity 内持久化玩家状态。

## 2. 交付物

### 2.1 追踪清单（Checklist）
生成一份“章节 → 条目 → 代码落点”的追踪清单，字段包含：
- `id`：稳定编号（例：`V51-02-2.1-01`）
- `spec_ref`：规格书章节/段落定位
- `requirement`：规格条目描述（可验证的表述）
- `status`：`todo | doing | done | blocked`
- `code_refs`：关键落点文件链接（file://…#Lx-Ly）
- `tests`：验证方式（手测步骤/自动测试/断言）
- `notes`：边界条件与限制

清单路径（计划）：`/workspace/doc/V51_IMPLEMENTATION_CHECKLIST.md`

### 2.2 阶段化提交（主干基线）
- 采用“章节/系统”为粒度拆分提交。
- 每个提交都要更新清单里对应条目的 `status` 与 `code_refs`。

说明：当前执行环境可能不包含 `.git`，无法直接在此处创建真实的 git 分支/提交；但仍会按“提交粒度”组织改动，并在清单与变更日志里提供等价的变更分组。若你在真实仓库执行，可按分组逐次提交到 `main`。

## 3. 实施顺序（从头到尾）

### Phase 0：硬约束收敛
目标：先确保铁律与架构约束不再被任何路径绕过。
- 方块唯一性：资源与注册只保留 `power_core`、`trade_terminal`
- 网络包：所有 C2S 都具备 sender/权限/距离/身份/输入校验
- Menu：`stillValid()` 按方块位置/距离校验，避免远程继续交互

### Phase 1：系统架构与事件/调度一致性
目标：与规格书结构保持一致，减少“随机位置执行逻辑”。
- Event Layer 集中化：逻辑由 EventHandlers 触发
- TickHandler 统一调度：各系统按固定频率 tick
- 系统间只通过 `PlayerData` + `WorldData` 交互

### Phase 2：数据持久化与离线处理
目标：长期数据正确、可恢复、可同步。
- Capability 保存/克隆/同步
- SavedData：契约、世界经济数据、离线收益
- 离线结算入口：登录时重算与补偿

### Phase 3：交互范式（核心与终端）
目标：所有玩法入口集中到两个方块。
- 核心 10 格强制接入 + 强制关闭逻辑
- 终端 GUI Tab：交易/职业/转账/批发/契约等
- 距离提示、失败回执、音效/粒子（按规格）

### Phase 4：玩法系统逐章完成
- 阶级与管控（遗民/受限/自由、低保、假票、信用修复、堕落事件、越界处罚、死亡税）
- 共生社会（扫描、亲密度、衰减、续签、减免）
- 税务与传送（周期税、里程税、维度税、跨维度）
- 职业绑定（6 职业、设备封锁、惩罚性关税、入职/离职制裁）
- P2P（转账税、奴隶禁汇、回执）

### Phase 5：低优先级补齐
包含但不限于：环境音效强化、离职音效反馈、随主权（30 格共享半径）、铁匠拆解等。

## 4. 安全与滥用防护（必须项）
- 所有 C2S 包：`sender != null`、输入字段长度/范围校验、关键行为限频
- 高敏操作（经济扣款/发放、契约、签证、越界处罚）：必须验证“处于正确交互范围/菜单仍有效/身份满足”
- 不在日志里打印敏感信息（不记录玩家可用于攻击的 payload 原文）

## 5. 验证与验收

### 5.1 本地/CI 构建验证（推荐）
在可访问 Forge Maven 的环境执行：
- `./gradlew build`
- `./gradlew runGameTestServer`

### 5.2 手测清单（最小闭环）
- 放置核心后全服初始资金/阶级是否正确
- 核心 10 格外能否被强制阻止所有行政行为
- 终端与核心走远后 menu 是否自动失效（stillValid）
- 伪造发包测试：远程发起核心操作/交易/契约是否被服务端拒绝

## 6. 风险与约束
- 由于执行环境网络限制，可能无法在此处完成 ForgeGradle 依赖拉取与构建验证；将以静态一致性检查 + 规格对齐为主。
- 若发现规格书内部自相矛盾，以“铁律”优先，其次以“系统架构/权威模型/数据中心化”优先。
